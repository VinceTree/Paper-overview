# 交互式代码讲解

仅在用户选择需要代码讲解，或已明确要求对照代码解释这篇论文时读取并使用。
这是 11 项概览之后的可选深入分支；用户只问局部代码时，从对应位置开始。

## 开始前与交互节奏

沿用用户已给出的知识背景、任务和例子偏好。没有指定场景时，默认选择论文自己的任务或
公开样本，不再为了选场景追加一轮确认。先说明本次追踪训练、推理还是分析脚本，
以及代码版本和静态阅读范围；一次只追踪一条主路径，按需再讲其他路径。

建议分成三个阶段，每次回复完成一个阶段：

1. **样本与入口**：说明具体任务、一条样本的内容、入口和需要经过的模块。
2. **关键计算**：沿调用顺序对照短代码片段，逐步解释对象如何改变。
3. **输出与下一轮**：把结果还原为任务含义，解释循环或训练更新，再对应回论文。

这三个阶段可以按实际复杂度拆分或合并。每轮末尾用一句话回顾已经走到哪里，
再提出一个与下一步相关的选择，例如“接着看这条样本如何进入预测器，还是先解释索引选择？”
提出选择后等待回复，不在同一轮继续下一阶段。
“继续”沿当前路线推进；追问先解决当前问题；跳转补最少前提；“不用了”结束代码分支。
用户要求一次讲完时可以合并交付，仍保留清楚的步骤。

## 阶段一：先看清一条样本与接口

先用一句具体任务说明输入和期待输出，例如“一段视频预测被遮挡区域的表征”，
避免只说模型名或数据集名。分析脚本可用“一行观测经过清洗后怎样进入统计量”作主线。

核查 README、入口、配置、数据读取与变换、核心计算和输出处理的位置，
只展示与本次样本有关的文件、函数和调用关系，不罗列整个目录树。
可用下表交代样本：

| 字段或对象 | 形状 / 类型 | 每维含义与单位 | 样本值及来源 |
| --- | --- | --- | --- |
| 按当前实现填写 | 区分原始形状与处理后形状 | 如批次、时间、空间、特征维 | 公开样本 / 配置 / 示意 |

优先使用可访问的公开样本或仓库自带例子。没有真实值就明确使用示意数字；
论文和代码都未给出的单位或含义写“未说明”，不靠猜测补齐。
不能为了讲解默认下载完整数据集或模型权重。

对象太大时缩成能手算的玩具尺寸，先说明缩小了什么，以及哪些结构关系仍保留。
例如可以减少样本数或序列长度，但若实现要求固定尺寸、整除或特定掩码布局，
须保留约束，或把玩具例子明确标为只说明机制的伪代码。
后续回到当前配置的真实尺寸；不能套用参考例子里的模型参数或历史行号。

## 阶段二：沿执行顺序走关键计算

讲解顺序由代码实际调用决定，通常可沿下面的链路追踪：

```text
原始样本 → 预处理 → 核心计算 → 输出处理 → 任务结果
```

在箭头上标清相关的形状变化、执行次数或时间位置。训练与推理路径不同就分开讲，
统计分析或证明助手代码则使用其真实的计算与依赖关系，不强加神经网络训练流程。

每一步都交代：

- **进入这一步时有什么**：对象的含义、具体值或形状；索引代表位置还是内容。
- **哪段代码做了什么**：给出已核实的文件、函数与行号，通常只贴 3–10 行必要片段，逐行解释。
  仓库片段与为教学改写的伪代码分别标注，链接尽量固定到本次读取的 commit。
- **出来后变成什么**：把数值或形状算出来，说明为什么需要这一步，并对应到论文的模块或公式。

关键公式先解释它约束什么，再解释符号与单位，必要时用小数字算一遍。
遇到容易误解的操作，单独用一句白话点明差异，如“这里是删掉选中的位置，
所以序列变短；这里没有把原位置填零”。这些判断必须来自当前代码。

与当前路径有关时，补充以下细节：

- 数据：归一化、分词、切片、填充、掩码、索引与维度转换。
- 训练：目标如何构造、损失如何聚合、梯度流向哪里、哪些参数冻结或单独更新。
- 推理：哪些计算只做一次，哪些重复执行，缓存保留什么，输出中哪些被选择或丢弃。
- 在线系统：区分一次模型调用、内部迭代和外部观测更新；频率与耗时有来源才给数字。

用户说“太抽象”时，换成更小的数字或更短的路径重新走；必要时先解释朴素方法为什么
不能满足这里的约束。不要只把原话加长。用户复述理解时，先判断是否正确，再纠正具体偏差。

## 阶段三：输出、多轮与论文对应

把输出翻译成任务中的可见结果，区分模型产生的内容、后处理和外部系统执行的动作。
若有循环，至少展示第一次调用和一次后续调用：新输入来自哪里，状态或缓存如何改变，
哪些量复用、重算或丢弃，以及何时停止。单次批处理或没有反馈的算法无需编造第二轮。

训练例子说明一次损失计算与参数更新如何衔接；没有执行训练时，不编造更新后的权重或性能。
末尾用一条短链串起整个样本的过程，再把玩具尺寸与实际配置对应起来。
指出论文与当前公开实现之间已经核实的差异，以及仍未核实的部分。
静态阅读、手算示意与真实运行结果必须分清。

## 节奏示例：一个可手算的玩具流程

下面是自写的教学伪代码与示意数字，不对应任何论文、官方实现或实测结果。
实际带读必须替换为当前论文的样本与已核实片段；不能给此例添加虚构的仓库位置。

用户回答“需要”后的**第一轮**可以这样开始：

> 我们先走一个输入有两维、输出一步预测的玩具例子。原始输入是 `[6, 14]`，
> 参考中心值是 `[4, 10]`，缩放值是 `[2, 2]`。这轮只看输入如何进入核心计算。
>
> 先记住三个位置：预处理负责换尺度，核心计算负责预测，输出处理负责还原单位。
> 接着看预处理的两行，还是先解释这三个数组各代表什么？

等待用户继续后，**第二轮**只讲关键变换：

```python
scaled = [(x - center) / scale
          for x, center, scale in zip([6, 14], [4, 10], [2, 2])]
prediction = 0.5 * scaled[0] + 0.25 * scaled[1]
```

> 第一行按维计算，得到 `[(6-4)/2, (14-10)/2] = [1, 2]`，长度仍是 2。
> 第二行把这两个数合成一个预测：`0.5×1 + 0.25×2 = 1.0`，输出从两维变成一个标量。
> 这里的权重只是教学设定，我们没有训练或调用模型。
> 现在得到的是换过尺度的结果。继续看怎样还原单位，还是先解释这两个权重？

再次等待后，**第三轮**收束到任务结果：

```python
result = prediction * 3 + 5
```

> 假设输出的缩放值是 3、中心值是 5，就得到 `1.0×3+5 = 8`。
> 整条链是 `[6,14] → 换尺度为 [1,2] → 合成为 1.0 → 还原为 8`。
> 如果真实任务有下一轮输入，要按真实代码说明它来自新的观测还是上轮结果；
> 这个玩具计算本身没有反馈循环。
